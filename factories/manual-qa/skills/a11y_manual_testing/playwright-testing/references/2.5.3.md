## Configuration

- WCAG: 2.5.3 Label in Name
- Level: A
- Testing mode: Pure Static
- Detection: Playwright Static
- Candidate discovery: DOM-based
- Interaction: None
- AI judgment for PASS/FAIL: No
- AI usage: None during classification

## Goal

Verify that, for user interface components with a visible text label, the
programmatic accessible name contains the visible label text.

A visible label and a programmatic accessible name are different concepts. A
component may have a visible label even when that label is not
programmatically associated with the component.

Example:

```html
<label>Name:</label>
<input type="text" name="name">
```

The visible label is `Name:`. If the input has no computed accessible name,
`accessibleName = ""` and the result is `FAIL`. Do not classify this situation
as `NOT_APPLICABLE`.

## Scope

Evaluate only the initial rendered page state.

Do not:

- click;
- type;
- hover;
- move keyboard focus;
- submit forms;
- open dialogs, menus, or popovers;
- expand collapsed content;
- trigger state changes;
- resize the viewport to expose another responsive state.

Only WCAG 2.5.3 is in scope. Do not report findings for other WCAG criteria.

## 1. Open the page

Use Playwright to open the exact URL provided by the user. Store the actual URL
analyzed by Playwright as `testedUrl`.

Wait until the page is sufficiently loaded for static analysis.

If authentication, security protection, network failure, application load
failure, or another blocking condition prevents access:

- stop the analysis;
- close the Playwright page and browser;
- record that the page could not be evaluated.

Do not interact with blocking UI in this Pure Static reference.

## 2. DOM candidate discovery

Candidate discovery must be DOM-based. Do not use the Playwright accessibility
snapshot as the source of truth for candidate discovery.

Using Playwright DOM inspection, explicitly collect all elements matching:

```css
button,
a[href],
input,
select,
textarea,
[role="button"],
[role="link"],
[role="textbox"],
[role="combobox"],
[role="checkbox"],
[role="radio"],
[role="menuitem"],
[role="switch"],
[role="slider"]
```

Consider every matching DOM element before accessibility-name evaluation. Do
not exclude an element merely because:

- it is absent from the accessibility snapshot;
- it has no accessible name;
- it has no exposed accessibility-tree role;
- it is incorrectly labeled;
- it has invalid accessibility implementation;
- it may ultimately fail this criterion.

A missing accessible name is evidence to evaluate, not a reason to exclude the
element. The Playwright accessibility snapshot may be used as supplementary
evidence but must not replace DOM candidate discovery.

Store `totalDomCandidates`.

## 3. Visibility filter

Apply the visibility filter to every DOM candidate.

Exclude elements that are:

- `display: none`;
- `visibility: hidden`;
- `opacity: 0`;
- `aria-hidden="true"`;
- inside hidden or collapsed containers;
- otherwise not visually rendered in the current page state.

Do not interact with the page to expose hidden content. Do not infer that an
element is hidden simply because it is missing from the accessibility snapshot.

Store `visibleCandidates`.

## 4. Determine the visible label

For every visible candidate, determine whether text is visually presented as
the label of that specific component. Store the result as `visibleLabelText`.

Visible-label detection is based on what is visually presented to the user. A
visible label does not need to be programmatically associated with the control
in order to qualify for WCAG 2.5.3 evaluation.

Do not require matching `for` and `id`, a wrapping `<label>`, valid ARIA
association, or an accessible name in order to recognize visible label text.

### Visible label sources

Use the following evidence in order.

1. **Associated visible `<label>`.** Use its rendered text.
2. **Wrapping visible `<label>`.** Use the label's rendered text.
3. **Nearby visible `<label>` in the same form row or container.** It may
   visually label the control even when the markup does not programmatically
   associate them. Missing `for`/`id` must not make the element
   `NOT_APPLICABLE`.
4. **Visible text immediately adjacent to the control.** Inspect visible text
   immediately before or after the control in the same logical row or
   container. For checkboxes and radios, following or preceding text may be the
   visible label.
5. **Button and link text.** Use visible rendered text.
6. **Button-like input value.** For `input[type="button"]`,
   `input[type="submit"]`, and `input[type="reset"]`, use the rendered value.

### Label selection rules

When multiple nearby text nodes exist:

- prefer a visible `<label>` element;
- prefer text in the same immediate form row or container;
- prefer the text visually closest to the control;
- prefer short label-like text over longer help or instructional text;
- for text fields, prefer label-like text immediately before the control;
- for checkboxes and radio buttons, prefer label-like text immediately before
  or after the control;
- do not concatenate unrelated text blocks.

Example:

```text
Security Test
Please enter the two words you see below, separated by a space.
[____________]
```

If `Security Test` visually functions as the field label and the longer
sentence is instructional text, use `visibleLabelText = "Security Test"`. Do
not use the instructional sentence as the visible label.

### Do not use as the visible label

Do not use:

- `aria-label`;
- non-visible `aria-labelledby` content;
- hidden text;
- visually hidden text;
- `title`;
- placeholder text by itself;
- CSS-generated `::before`;
- CSS-generated `::after`;
- distant page text;
- unrelated help text;
- unrelated instructional text;
- group descriptions that do not label the specific control.

### NOT_APPLICABLE

Use `NOT_APPLICABLE` only when the component genuinely has no visible textual
label.

Do not use `NOT_APPLICABLE` merely because:

- the visible label is not programmatically associated;
- `for`/`id` association is missing;
- the accessible name is missing;
- the component is absent from the accessibility snapshot.

### NOT_EVALUATED

If visible text exists around the component but it is genuinely unclear which
text functions as its visible label, use `NOT_EVALUATED`. Do not guess.

Store `visibleLabelText` and the label evidence or source when useful.

## 5. Determine the accessible name

For every candidate with a qualifying visible text label, obtain its
browser-computed accessible name using Playwright or browser accessibility
information.

Store:

- `visibleLabelText`;
- `accessibleName`;
- `role`;
- `locator`.

For confirmed failures also retain, when useful:

- element tag;
- explicit role;
- `aria-label`;
- `aria-labelledby`;
- associated `<label>`;
- relevant HTML snippet.

An empty computed accessible name is a valid result. Do not:

- infer the accessible name from visible nearby text;
- substitute `visibleLabelText`;
- replace an empty accessible name;
- exclude the element because the accessible name is empty.

For example, `visibleLabelText = "Name:"` and `accessibleName = ""` is valid
evidence and must continue to classification.

If the computed accessible name cannot be obtained because of a technical
failure, classify the candidate `NOT_EVALUATED`. Do not guess.

## 6. Determine semantic role

Determine the semantic role for each qualifying candidate. Use a valid explicit
ARIA role when present; otherwise use native HTML semantics.

Examples include `button`, `link`, `textbox`, `combobox`, `checkbox`, and
`radio`.

Do not exclude an element because its role is not exposed in the accessibility
snapshot if its native or explicit DOM semantics are known.

## 7. Normalize values

Normalize `visibleLabelText` and a non-empty `accessibleName` using
deterministic string processing only:

- convert to lowercase;
- trim leading and trailing whitespace;
- collapse repeated whitespace;
- ignore non-essential punctuation where meaning is unchanged;
- preserve logical word order.

Treat `&` and `and` as equivalent when they clearly represent the same visible
wording.

Example: visible label `Pickup & Delivery` and accessible name
`Pickup and Delivery options` results in `PASS`.

Do not use semantic AI interpretation during normalization.

## 8. Deterministic classification

Every visible candidate receives exactly one final classification:

- `PASS`;
- `FAIL`;
- `NOT_APPLICABLE`;
- `NOT_EVALUATED`.

The agent must not determine or override classification outside the following
rules.

### FAIL — missing accessible name

If `visibleLabelText` is not empty and `accessibleName` is empty, classify
`FAIL` with failure type `missing_accessible_name`.

Do not classify this as `NOT_APPLICABLE` or `NOT_EVALUATED`.

### PASS

If `accessibleName` is not empty and the normalized accessible name contains
the normalized visible label while preserving logical word order, classify
`PASS`.

Additional descriptive text is allowed:

- visible label `Search`, accessible name `Search products` → `PASS`;
- visible label `Delete`, accessible name `Delete customer record` → `PASS`.

### FAIL — label/name mismatch

If `accessibleName` is not empty and the normalized accessible name does not
contain the normalized visible label, classify `FAIL` with failure type
`label_name_mismatch`.

Example: visible label `Search`, accessible name `Find products` → `FAIL`.

## 9. Classification safeguards

PASS/FAIL classification must follow the rules above. In particular:

- visible label plus empty accessible name equals `FAIL`;
- missing programmatic label association does not mean `NOT_APPLICABLE`;
- absence from the accessibility snapshot does not mean `NOT_APPLICABLE`;
- inaccessible controls must not disappear from evaluation because they are
  inaccessible.

The agent must not:

- change `PASS` to `FAIL`;
- change `FAIL` to `PASS`;
- reinterpret the comparison using semantic judgment;
- invent missing evidence.

## 10. Candidate processing validation

Retain:

- total DOM candidates;
- visible candidates;
- candidates with qualifying visible labels;
- `PASS`;
- `FAIL`;
- `NOT_APPLICABLE`;
- `NOT_EVALUATED`.

Verify that every visible DOM candidate reaches one of `PASS`, `FAIL`,
`NOT_APPLICABLE`, or `NOT_EVALUATED`. Candidates must not silently disappear.

If DOM discovery cannot be completed, record:

`Analysis incomplete: DOM candidate discovery could not be performed.`

If candidate processing is inconsistent, record:

`Analysis incomplete: candidate processing was inconsistent.`

Do not produce a no-issues result from incomplete analysis.

## 11. Store results

For `PASS` and `FAIL`, retain:

- result;
- visible label;
- accessible name;
- role;
- locator.

For `FAIL`, also retain the failure type and relevant implementation evidence
when available.

Store summary counts:

- total DOM candidates;
- visible candidates;
- elements evaluated;
- `PASS`;
- `FAIL`;
- `NOT_APPLICABLE`;
- `NOT_EVALUATED`.

Define `elements evaluated = PASS + FAIL`. Do not include `NOT_APPLICABLE` or
`NOT_EVALUATED` in elements evaluated. Also retain `testedUrl`.

Pass these stored results to the parent skill. Do not group findings, prepare
bug data, generate recommendations or reproduction steps, or create a report in
this reference.

## 12. Close Playwright

After evidence collection, validation, and classification:

- store all required evidence;
- store all counts;
- store the exact `testedUrl`;
- close the Playwright page;
- close the Playwright browser or session.

All subsequent processing must use stored evidence only.
